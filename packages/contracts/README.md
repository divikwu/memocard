# MemoCard bridge v1 — M0/M1 contract

Native requests: `{version:1,requestId,operation,params}`. Replies: `{ok:true,data}` or `{ok:false,error:{code,message,retryable}}`.
Swift core exposes `public actor VaultStore`, `init(localDataURL: URL) throws`, `open(url: URL, create: Bool) throws`, and `perform(operation: String, params: Data) throws -> Data`. The returned Data is JSON **data**, not the reply envelope. Public `VaultError` exposes `code`, `message`, `retryable`. Host wraps errors. Host/UI operations are separate from core operations.

Local Web adds an optional actor-internal binding: `open(url:create:binding: UUID = UUID())`, `perform(operation:params:expectedBinding: UUID? = nil)`, and `asset(relativePath:expectedBinding: UUID? = nil)`. NativeHost passes its vault-open generation to Web calls. Core validates it before dispatch without suspension; switching directories invalidates old requests even when restored vault copies share the same `vaultId`. Legacy native call sites may omit the argument.

M1 core: `getStatus {}`, `queryNotes {query?,tags?,from?,to?,limit?,cursor?,deleted?}`, `getNote {id}`, `saveNote {id,body,tags,baseHash: string|null}`, `listTags {}`, `saveDraft {id,body,tags,baseHash,relativePath?}`, `getDrafts {}`, `importAttachment {name,base64,noteId?}`. Draft `relativePath` is optional rendering context, never an authoritative save destination. Attachment result `{relativePath,markdownPath,notePath}`; the core resolves `noteId` to its current location and returns a Markdown path relative to that note's directory. The editor updates its rendering and draft context from returned `notePath`, including when the file moves during editing. Missing/new IDs use the default `notes/` directory. Unsupported image types are rejected before writing. Supported imports are PNG, JPEG, WebP, GIF, HEIC and HEIF.

Native core and authenticated Local Web expose `dismissDraftReminder {id,draftKey,revision,unscoped?,scope?}` when advertised in capabilities. This stores a device-local reminder preference for the current directory instance and exact draft file fingerprint; it does not modify or delete the draft or source note. A changed revision rejects stale requests with `DRAFT_CHANGED`. `getDrafts` derives optional `reminderDismissed:true` only while the fingerprint matches. Suppressed records remain in the recovery list; changed drafts, another directory instance, or unreadable preference metadata retain reminders. This operation is not available through the read-only MCP server.
Query is literal case-insensitive body substring, tags AND, createdAt descending then id ascending. `from` is inclusive and `to` is exclusive. Pages observe both the requested count limit and a 2 MiB encoded-note budget; one larger valid note may be returned alone. Always follow `nextCursor`, even when a page contains fewer than `limit` notes. Content hash is SHA256 of source bytes.
`queryNotes.sort` accepts `createdAt` (default), `updatedAt`, or `pinnedAt`; dates sort descending with ID ascending as a stable tiebreaker. `pinned?:boolean` filters before pagination, and `pinnedAt` includes only pinned notes. Date ranges still refer to creation dates. Cursor fingerprints include update dates or pin metadata when the chosen query depends on them.

`deleteNote {id,baseHash,vaultId?,vaultBinding?}` moves an existing source into `.memocard/trash/<uuid>/<original-relative-path>` after verifying the current hash and a complete, unambiguous scan. It returns `{id,relativePath,trashPath}`; native Swift also returns `trashKey` and the reviewed `contentHash` for MCP verification. Native/Local Web use a coordinated move; the browser verifies a durable byte-for-byte backup before removing the original. Attachments and other drafts remain intact. The hidden recovery directory is excluded from note, tag and pin queries. Each new deletion also records original identity, creation and deletion dates in `entry.json` beside the archived hierarchy. The recycle-bin UI can list, preview and restore archives; older archives without metadata remain supported, using a stable archive UUID when an Obsidian local identity is unavailable. Detail UI flushes pending edits before requesting deletion and returns to its previous collection after success. MCP exposes recoverable deletion and restoration only with explicit write consent and the current vault/instance binding; permanent deletion remains unavailable through MCP.

`getTrash {vaultId?,vaultBinding?}` returns `{notes:TrashItem[],issues}`; each item contains `trashKey`, source ID/title/path, deletion date, content hash and a short preview. `getTrashedNote {trashKey,vaultId?,vaultBinding?}` returns `{trashKey,deletedAt,note}` for read-only rendering using the original note path. `restoreNote {trashKey,baseHash,vaultId?,vaultBinding?}` returns the restored Note, verifies the reviewed bytes and preserves Markdown exactly. An occupied original path gets a collision suffix; existing source identities cannot be duplicated. A durable rename journal rolls file and identity changes back on failure. These operations are scoped to the current vault, validate archive keys and do not expose arbitrary hidden paths. Broken archives remain on disk and surface as list issues. `permanentlyDeleteNote {trashKey,baseHash,vaultId?,vaultBinding?}` removes only the reviewed archived Markdown after another hash check and returns `{deleted:true}`. The UI requires an explicit confirmation that the action cannot be undone. Shared attachments, active notes and sibling archives remain untouched. A failed or stale request leaves the record available for retry. Empty-trash is not provided.

`deleteDraft {id,draftKey,revision,unscoped?,scope?,vaultId?,vaultBinding?}` deletes only the selected device-local draft after UI confirmation. Native, Local Web and browser storage advertise this capability. The exact key, recovery scope and revision are verified; newer or missing records reject with `DRAFT_CHANGED`. Source notes, other drafts and attachments remain untouched. Legacy browser drafts expose a derived revision until their next write. The operation is unavailable through read-only MCP.

`getNotePins {}` returns `{pins:Record<noteId,ISODate>,contentHash}` for existing, non-deleted notes. `setNotePinned {id,pinned:boolean,baseHash,vaultId?}` uses metadata hash comparison and rejects incomplete scans, missing notes, stale hashes and mismatched vaults. Idempotent pinning retains its timestamp. `.memocard/pins.json` stores pins independently of Markdown: version 1 uses note UUID keys; compatible version 2 uses `path:<relativePath>` keys shared across local note identities. MemoCard title renames update these keys within the existing rename transaction. External file moves are not inferred as pin moves. Pinning does not change source hashes or update dates. The UI exposes this operation only in the detail header; the home tabs share the existing card/list collection. Pins are vault data, not device-local preferences; filesystem synchronization uses the vault's existing sync mechanism.
`queryNotes.quickFilter` optionally accepts `untagged`, `images`, or `links`, combined with the existing search/tag/date conditions before pagination. Replies include `filterCounts: {untagged,images,links}` for all indexed, non-deleted notes, independent of the current search and page. Views may overlap. Images include Markdown inline/reference images, Obsidian image embeds and HTML images; links include Markdown links, wikilinks and HTTP(S)/www URLs. Code and HTML comments are excluded; an image URL alone does not count as a link.
Bare URL markers (`http://`, `https://`, `www.`) accept ASCII case variants; Unicode lookalikes such as `httpſ://` are not markers. Unicode hosts and paths remain supported. Native and browser classification share the cases in `tests/fixtures/note-filters-unicode.json`.
Host: `selectVault {create:boolean}` (create Mac only), `getEnvironment {}` (platform, phase, mcpEnabled), `setMCPEnabled {enabled:boolean}` (Mac; directory picker when enabling), `pickImage {noteId?}` (native picker; attachment result), `openExternal {url}`, `getAsset` handled by native scheme, not arbitrary filesystem reads.
`window.webkit.messageHandlers.memocard.postMessage(request)` returns Promise<reply>. Native events use `window.dispatchEvent(new CustomEvent('memocard:event',{detail:{type:'notesChanged'|'statusChanged',...}}))` with structured arguments, never source concatenation. Local UI scheme `memocard-ui://app/index.html`; attachment scheme `memocard-asset://vault/<relativePath>`; deep links `memocard://note/<id>?vault=<vaultId>`.

The UI registers `memocard:open-note` before calling host `uiReady {}`. Native queues cold-launch links until ready and verifies the selected vault. The event carries `{id}` only; it never supplies a filesystem path or a write operation.

Local Web uses the menu bar service's loopback HTTP server, with a one-use fragment token exchanged at `POST /api/session` for an HttpOnly SameSite=Strict cookie. `POST /api/bridge` carries the same bridge envelope; same-origin authenticated attachments use `/api/assets/<relativePath>`. Its operation allowlist covers core note/draft/image operations and host-advertised vault actions. Browser file selection and safe external links are handled in the browser; directory selection remains native. The menu bar service supports `selectVault`, `listVaults`, and `activateVault`, while Mac App-only MCP settings remain native. `memocard-service://open-web` asks the installed menu bar service to create a fresh authorized page; the Mac App compatibility entry `memocard://web` delegates to that same command and does not start another server. Neither accepts file paths or return URLs. See `docs/LOCAL_WEB.md` for lifetime, limits and recovery behavior. MCP TCP authorization and read-only operations remain separate.

M1 UI includes honest setup/empty state, draft+save, cards/search/preview, native image import, status and MCP toggle. No mock persistence or fake completed statistics/trash. M2/M3 operations stay unavailable until platform gate passes.

TCP request: `{version:1,requestId,token,instanceId,vaultId,operation,params}` serialized as one UTF-8 JSON line. Reply is `{requestId,...bridgeReply}` plus newline. Authenticate token, instanceId AND vaultId before any data. Read-only operations only: getStatus, queryNotes (deleted always false), getNote (reject deleted), listTags. Request frame maximum 8 MiB; response maximum 62 MiB to accommodate JSON escaping of a valid 8 MiB note. Oversized responses return `RESPONSE_TOO_LARGE`. Timeout 15 seconds. Bind only IPv4 127.0.0.1 on ephemeral port, no Bonjour. Configuration is exported outside vault/repositories, mode 0600.

MCP tools: get_status, search_notes, get_note, list_tags. Complete serialized tool results are capped at 8 MiB for compatibility with default SDK clients. Oversized single-note results return `RESPONSE_TOO_LARGE`, never truncated content. MCP stdout protocol only. Node adapter rereads connection config for each call, validates loopback host and port. Connection file supplied by `--connection-file /absolute/path`. M1 smoke verifies protocol against actual Mac App; fixtures never count as iCloud or iPhone acceptance.

## Obsidian-compatible folders (2026-09-29)

Manifest version 2 scans Markdown from the vault root; frontmatter is optional and user-owned. Note API IDs and creation timestamps come from device-local identity records, never required source properties. Version 1 retains its original rules. `resolveLink {target, sourcePath, wiki?}` returns `{kind:"note",id,path}` or `{kind:"image",path}`; ambiguous/missing links fail explicitly. This is a UI bridge operation, not an MCP write capability. Version 2 attachments may reside anywhere non-hidden inside the authorized root. See `docs/OBSIDIAN_COMPATIBILITY.md` for preservation, identity and concurrency boundaries.

Nested tags use `/` separators. `queryNotes.tags` matches each requested tag or its descendants (for example `work` includes `work/design`, but not `workshop`); multiple requested tags still use AND semantics. `listTags` includes implicit ancestors and counts distinct notes per ancestor, not the sum of child counts. This applies to both browser and Swift stores without rewriting tags in Markdown.

Page titles: `Note`, `saveNote` and recovery records accept optional `title:string`. Omission preserves the existing filename; an empty string uses `新内容`. The page title is the filename without `.md`, independently of YAML `title` and the Markdown body. New filenames use only the manually entered title, defaulting to `新内容` with a collision suffix when needed; body headings are never promoted or removed. New UI pages explicitly send `title:""` and remain unsaved until the user enters a non-blank title or body. Manual title changes rename the file while preserving its ID; body-only edits preserve the filename. Recovery matching includes title so an older body-identical save cannot discard a newer title edit. Searches include titles.

New-note `saveNote` and `saveDraft` requests accept optional `inheritedTags:string[]`. Recovery preserves them separately from body tags. On first source creation they become YAML `tags`, without appending text to the body; later body saves preserve the existing tag property. An untouched UI draft with only inherited tags does not create a source file.

`getNote`, `saveNote`, `saveDraft`, and `importAttachment` accept optional `vaultId` and `vaultBinding` to reject a request targeting another library or directory instance before dispatch. Native and Local Web `getEnvironment` expose the current opaque `vaultBinding`, matching the browser directory adapter. Quick capture retains this binding through image selection, source commits and uncertain-commit verification. It keeps unsubmitted content in page memory without writing device-local recovery; source creation requires the Record action or its keyboard shortcut, and a successful commit clears the composer and refreshes the recent-update query from its first page.

Property duplication uses `create:true` with `copyFrom` naming an editable custom property in the same hash-verified note. This permits retaining the source list's literal values and duplicate counts; it does not permit adding invalid values or extra duplicates. Library option renames preserve those counts after mapping the verified original values to the new option name.
