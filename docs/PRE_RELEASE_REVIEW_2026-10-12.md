浏览器源事务持有索引锁，避免轮询把尚未完成的保存当作中断事务恢复；错误时先终止暂存流，再进行回滚。新增并发测试确认保存期间发起查询时，查询最终看到已提交正文和哈希。普通自动保存只保留当前恢复事务，不为每次输入积累永久全文备份；已有重命名/批量操作的备份行为保留。

另修正恢复选择器说明：只有标明“尚未绑定目录”的版本需要确认目录归属，避免把正常多客户端草稿统一描述为未绑定。此文案修改后 App 的 55 项测试再次通过。

## 复审覆盖与保留边界

- 保存队列：正文与属性共用顺序、旧响应不能覆盖最新输入、失败重试、冲突续写、重新加载、另存副本与恢复清理顺序。
- 属性：全库转换先检查无损性，失败不写源或定义；响应属性快照、定义哈希与后续排队意图同步。
- 本机恢复：每客户端范围、目录副本/移动/旧记录、坏草稿隔离、源事务受阻时草稿仍可读写。
- 存储提交：源写前版本检查、日志提交点、身份落盘失败、响应丢失、回滚遭遇外部第三种内容的保护。
- 性能与刷新：APFS 索引的拓扑和文件时钟核验、损坏/重复身份写入门槛、分页新游标链、刷新与加载更多串行、滚动锚点。

复审由当前代理进行第二遍检查，没有委派其他代理，也没有获得另一位人工审查者的签字。测试覆盖与代码复审不能证明所有并发调度、文件提供商和硬件故障均无问题。

浏览器 File System Access API 仍缺少与外部程序共享的操作系统级 compare-and-swap；最终核验与关闭写流之间的外部竞争窗口仍存在，本轮未宣称消除。失败回滚遇到第三种外部内容继续保留事务，不能盲目覆盖。

## 真实库隔离副本验收

读取 iCloud Drive 中现有 `MemoCard-M1-Test-20260928` 测试库，复制到被 Git 忽略的本机验收目录；**80 个文件、67 篇 Markdown、430,156 字节**，初始逐文件 SHA-256 与源库一致。库为格式 1；本次真实副本结果不能替代格式 2 的云同步验收。格式 2 的原生恢复测试及独立浏览器事务测试另行覆盖。

在副本上运行生产 `VaultStore`：

1. 对现有笔记执行 12 轮正文与 summary 连续保存，每次响应哈希与磁盘 SHA-256 相同。
2. 另一逻辑客户端保存独立正文和属性草稿；其过期源提交返回 `HASH_CONFLICT`，不能覆盖新源。
3. 文件系统原子写入模拟外部编辑，旧哈希提交被拒绝，外部字节保留。
4. 关闭并创建新 store，正文、属性、身份与哈希一致，另一客户端草稿仍完整存在。
5. 对照清单，79 个未参与编辑的原文件完全不变。宿主启动运行了两轮相同序列；原始 JSON 保留最后一轮的 12 次结果，不把两轮当独立性能采样。

生产 UI + 本机 HTTP 服务的浏览器验证：选择独立冲突版本，确认出现冲突保护，再执行“另存副本”。重载该副本后，正文为 `Client B pending recovery`、summary 为 `Client B pending`、无错误提示。磁盘原笔记的连续编辑和外部标记保留；所选恢复及其本次临时版本清理，另一份客户端版本仍保留。源库的 **80 个文件最终再次全量校验，完全未变**。临时服务和代理创建的浏览器标签均已关闭，访问令牌临时配置已移除。

这里的多客户端是同一生产 store 上的独立客户端意图及草稿范围，不是两个物理设备的云同步；外部编辑部分是文件系统写入，不能称为已实际操作 Obsidian。

2. 在 MemoCard 修改同一属性和正文；Obsidian 自动接收修改。关闭并重开 Obsidian 笔记，反向保存的正文和属性仍完整。

6. 最终逐文件核验：原 iCloud 测试库 **80 文件完全未变**；隔离副本仅目标 Markdown 和 Obsidian 自身 `.obsidian/workspace.json` 变化，其他 **78 文件（含 66 篇 Markdown）完全未变**，无新增文件。关闭临时浏览器和 Obsidian 副本窗口，恢复原 Obsidian 窗口；停止验收服务并删除临时访问配置。
