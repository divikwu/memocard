## 1. 结论与判定边界

> 后续大库优化：原生首次索引现支持进度反馈、首批笔记提前编辑、本机草稿独立保存、校验后自动提交及后台派生索引；新增 10 项回归，完整检查 UI 662 / 原生 97 项通过。性能与限制见 [大库首次打开与后台索引优化](BACKGROUND_INDEX_OPTIMIZATION_2026-10-12.md)。以下仍保留原审查时结论，不代表最新性能。

MemoCard 已具备完整的本地 Markdown 编辑与保存主链路。正文和属性统一排队、保存前记录恢复意图、源文件哈希校验、原子替换、批量修改事务日志、浏览器授权及路径限制，都有实现和自动化验证。隔离真实浏览器验证中，属性保存失败时仍能继续编辑标题、正文与另一属性；恢复服务后重试，最终源文件与重新打开的界面一致。

但“单个编辑器内保存一致”尚不能扩展为“多客户端、异常恢复与大库均可靠”。本次确认 **9 项问题：3 项 P1、6 项 P2**。优先风险是多客户端草稿覆盖、库级属性类型转换造成值丢失，以及源事务恢复受阻时连本机草稿操作也被阻断。性能方面，万篇本地库首次状态扫描超过普通请求的 15 秒期限，热态单条读取与写入仍需秒级时间。

建议先完成恢复隔离、破坏性批量变更保护及提交结果一致性，再推进增量索引。仅解除整页禁用能够改善操作感受，不能消除这些底层风险。

本次没有在已执行范围内确认 P0。此结论不代表所有平台、云提供商、并发时序或恶意输入都已覆盖，也不能作为数据永不丢失的保证。问题按实际触发条件分级，未实现的路线图功能另列，不计为当前功能缺陷。

## 3. 实际架构与状态语义

```text
React / Tiptap 编辑器
  → EditorSession：正文、属性意图、恢复记录的单编辑器串行队列
  → Bridge
      ├─ WKWebView → NativeHost → VaultStore
      ├─ 本地浏览器 → LocalWebServer / ServiceHost → VaultStore
      └─ 浏览器文件模式 → BrowserVault → File System Access + IndexedDB

VaultStore → NSFileCoordinator + 文件哈希 + 原子文件写入
          → 本机草稿、身份映射、事务日志
Markdown / 附件 / 库级属性配置 → 外部文件同步提供商（如 iCloud）
只读 MCP → 本地 TCP 读取服务 → VaultStore
```

Markdown 文件是内容来源，现有缓存不是独立的权威数据库。兼容模式将笔记身份记录保存在本机，保留原始 YAML；旧格式继续支持 YAML 中的身份信息。活跃编辑界面使用 Tiptap，仓库中保留的 CodeMirror 编辑器不能代表当前主要编辑路径。

`EditorSession` 的串行范围是一个编辑器实例，不是整个库或全部浏览器客户端。原生 actor 对单个 store 的操作串行化，不能替代客户端恢复记录隔离，也不构成跨进程或跨设备事务。

“已保存”应解释为当前源文件写入已完成。“本机草稿已保留”是另一项结果；“云端已上传、其他设备已收到”又是不同结果。当前 `syncState` 的本地读取覆盖状态没有云端上传确认能力，不应以它推导跨设备同步完成。

## 5. 已确认问题

### F01 · P1 · 原生多客户端的同一笔记草稿互相覆盖

**触发与影响。** 两个窗口或本地 Web 客户端同时编辑同一笔记，并在源提交前各自留下不同输入。后写入的恢复记录覆盖先写入者。源文件哈希冲突保护仍在，但第一个客户端崩溃后，其独立输入已没有对应恢复版本。

**证据。** 隔离 harness 对生产 `VaultStore` 连续执行两次 `saveDraft`，传入同一笔记 ID、不同 `draftKey` 和正文 A/B。`getDrafts` 仅返回 1 份，正文为 B；源文件保持原样。不是源文件并发覆写，也不是模拟的队列行为。

**根因。** [VaultStore.swift:919](/Users/divikwu/diw/workspace/memocard/packages/native-core/Sources/MemoCardCore/VaultStore.swift:919) 将目标固定为 `<vaultId>/<noteId>.json`，原生模型未落实客户端草稿键。浏览器直接文件模式已使用会话草稿键，不能据此认为原生路径同样隔离。

**建议与验收。** 将恢复记录按库实例、客户端/草稿身份隔离，同时保留笔记 ID 用于关联；不要简单把客户端草稿并成最后写入一份。两个客户端不同正文和待保存属性在重启后均可恢复；一方源提交只能清理它对应且内容匹配的草稿，不能删除另一方未提交输入。

### F02 · P1 · 属性类型切换会无预览地丢弃全库不兼容值

**触发与影响。** 在一篇笔记中将文本属性改为日期，会修改整个库中同名属性。不合法的日期文本转换为空值；多选转单选等转换同样可能缩减信息。用户没有在提交前看到影响范围和损失数量。

**证据。** 两份生产 Markdown 的 `summary` 分别为 `important-alpha` / `important-beta`，对其中一份执行类型定义切换后，两份原值均不再存在。事务正常结束，原生日志已清理，没有生成长期保留的变更前备份。结果见 `global-lossy-type-conversion`。

**根因。** [NoteProperties.tsx:167](/Users/divikwu/diw/workspace/memocard/apps/ui/src/NoteProperties.tsx:167) 直接提交 `definition:true`；[VaultStore.swift:718](/Users/divikwu/diw/workspace/memocard/packages/native-core/Sources/MemoCardCore/VaultStore.swift:718) 遍历全库修改；[NoteProperties.swift:329](/Users/divikwu/diw/workspace/memocard/packages/native-core/Sources/MemoCardCore/NoteProperties.swift:329) 将不兼容日期值转换为空；[VaultStore.swift:758](/Users/divikwu/diw/workspace/memocard/packages/native-core/Sources/MemoCardCore/VaultStore.swift:758) 在成功后删除临时回滚日志。

**边界。** 事务日志保障中途失败的回滚，并不提供成功后撤销。浏览器路径有保留备份记录的实现，但也没有本次所需的完整影响预览和恢复交互；不能把原生“无保留备份”结论泛化为所有路径完全没有备份。

**建议与验收。** 提交前显示作用范围、受影响笔记数、不可逆转换样例与数量；默认保留不兼容值或阻止有损转换，显式批准后才转换。保留可恢复的变更前版本。覆盖文本→日期、多选→单选、选项删除，并验证成功后的撤销以及异常中断后的恢复。

### F03 · P1 · 源事务恢复受阻会连带阻止本机草稿读取和保存

**触发与影响。** 重命名/批量事务中断后，外部编辑使某文件既不等于日志中的 before，也不等于 after。停止回滚以保护外部编辑是正确行为；但此时读取与保存本机恢复记录也被拒绝，新输入失去了该持久化出口。

**证据。** 在独立库构造有效的中断日志并写入第三种外部内容，生产 `getDrafts`、`saveDraft` 均返回 `RENAME_RECOVERY_REQUIRED`，已有草稿仍在磁盘。分别记录为 `blocked-rename-recovery`；未实际破坏用户文件或让测试输入丢失后才推断。

**根因。** [VaultStore.swift:158](/Users/divikwu/diw/workspace/memocard/packages/native-core/Sources/MemoCardCore/VaultStore.swift:158) 在分派所有操作之前无条件调用 `recoverRename()`；[VaultStore.swift:809](/Users/divikwu/diw/workspace/memocard/packages/native-core/Sources/MemoCardCore/VaultStore.swift:809) 的源文件保护异常因此阻断了与源写入无关的本机恢复操作。

**建议与验收。** 保持源事务冻结与外部版本保护，允许独立的草稿读写/导出，并显示明确的恢复原因。挂起日志时仍能保存最新正文和待保存属性；重启后可取回；源文件不被自动回滚覆盖。再提供可理解的事务恢复入口。

### F04 · P2 · 复制库与原库共享原生恢复记录范围

**触发与影响。** 复制整个库目录会保留 `.memocard/vault.json` 中的 `vaultId`。打开副本时能看见原库的本机草稿，库实例边界不明确。

**证据。** 同一本机恢复目录下，先在原库写草稿，再打开字节复制的独立目录，生产 `getDrafts` 返回原库草稿，`foreignDraftVisible:true`。普通兼容笔记的本机 ID 可能在副本中不同，因此本次不声称副本已被自动覆写；旧格式保留相同笔记 ID 时的错误恢复/提交属于需要进一步端到端验证的风险。

**根因。** [VaultStore.swift:910](/Users/divikwu/diw/workspace/memocard/packages/native-core/Sources/MemoCardCore/VaultStore.swift:910) 的草稿范围仅使用 `vaultId`，而 [VaultStore.swift:1036](/Users/divikwu/diw/workspace/memocard/packages/native-core/Sources/MemoCardCore/VaultStore.swift:1036) 的身份记录已同时使用目录与库 ID。

**建议与验收。** 明确“同库移动”和“独立副本”的身份规则，使用库实例范围隔离恢复记录；迁移旧草稿时保留可查性。原库、副本、移动后的库分别测试，不能为了隔离副本而使正常移动后的草稿无法找回。

### F05 · P2 · 一份损坏草稿会阻止正常笔记打开

**触发与影响。** 恢复目录里任一 JSON 损坏，整次 `getDrafts` 失败。启动流程将恢复列表作为路由就绪条件，导致正常源笔记也无法打开。

**证据。** 原生验证中，一份有效草稿旁新增 `{truncated`，`getDrafts` 返回 `IO_ERROR`，有效草稿仍在磁盘，直接 `getNote` 仍成功。生产服务加生产 UI 的隔离浏览器重载后显示通用文件错误、正文编辑器不存在；移除这份合成坏记录后可再次打开。截图为 `corrupt-draft-blocks-open.png`。

**根因。** [VaultStore.swift:931](/Users/divikwu/diw/workspace/memocard/packages/native-core/Sources/MemoCardCore/VaultStore.swift:931) 未隔离单条解码失败；[App.tsx:135](/Users/divikwu/diw/workspace/memocard/apps/ui/src/App.tsx:135) 在设置 `routeReady` 前等待整个恢复列表成功。

**建议与验收。** 返回可读草稿及逐条异常，保留坏文件供诊断和导出；恢复列表故障不应阻止只读打开正常源文件。一个坏记录加两个好记录时，两个好记录仍可恢复，源笔记可打开，界面能定位异常而不只显示泛化的权限错误。

### F06 · P2 · 源文件已提交，本机身份写入失败却返回整体保存失败

**触发与影响。** 兼容模式中，源写入成功后身份映射落盘失败。界面得到失败，仍持有旧哈希；用户重试会转成冲突，无法准确知道源内容究竟是否保存。

**证据。** 预热独立库后，将本机身份文件路径替换成同名目录以模拟该写入边界失败。`saveNote` 返回 `IO_ERROR`，但重新读取源字节确认新正文已提交，恢复记录仍保留。恢复身份文件后，使用原哈希重试返回 `HASH_CONFLICT`。这是受控的提交后故障，不等同于已做真实磁盘满或硬件断电实验。

**根因。** [VaultStore.swift:597](/Users/divikwu/diw/workspace/memocard/packages/native-core/Sources/MemoCardCore/VaultStore.swift:597) 先写源文件，再执行可抛错的 `persistIdentities`；属性路径在 [VaultStore.swift:792](/Users/divikwu/diw/workspace/memocard/packages/native-core/Sources/MemoCardCore/VaultStore.swift:792) 也有相同提交顺序。实测覆盖正文，属性影响为同构代码推断。

**建议与验收。** 明确源提交点和提交后本机元数据故障的返回语义；能够重读并确认已提交版本，或使用可恢复的事务设计。不能把所有错误都转为盲目重发。分别注入提交前、源提交后、身份写入后、响应丢失故障，确认无二次改写、无错误覆盖，且恢复记录清理正确。

### F07 · P2 · 大库扫描进入单条操作路径，首次请求可超过默认期限

## 8. 同步、兼容与故障恢复判断

### 已有保护

- 原生写前校验原始源字节哈希，拒绝旧版本覆盖；检测重复身份、待下载、文件版本冲突和不完整扫描。
- `NSFileCoordinator` 协调相关文件操作；不把协调写入等同于外部提供商完成上传。Apple 的机制说明见 [NSFileCoordinator](https://developer.apple.com/documentation/foundation/nsfilecoordinator)。
- 本机恢复数据与同步库目录分离，待保存属性随草稿保留；源提交后只尽力清理匹配草稿。
- 批量重命名/定义修改有日志，并在检测到外部第三种内容时停止回滚，保护外部版本。
- 浏览器文件模式使用 Web Locks 约束同源写入，写入前再次校验；保存提交与 `close()` 相关，参见 [File System Access](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access)。Web Locks 不约束 Obsidian 或其他原生进程，不能据此声称跨应用原子比较并交换。

### 应明确的产品状态

建议区分“正在编辑 / 本机草稿已保留 / 正在保存 / 已写入本机文件 / 保存受阻 / 发现外部版本”。只有存在可验证的提供商上传与远端收敛证据时，才显示对应的云同步完成状态。

当前只读不完整库、拒绝不安全写入，是保守的数据保护政策，不能简单当作故障去移除。问题在于用户还缺少逐文件诊断和恢复操作闭环，而 F03 又会连带阻断本机恢复；应解决恢复出口，保留源保护。

**代码检查后仍待验证的风险。** `NativeHost` 保存单个弱 `webView`，而 app 使用 `WindowGroup`，多窗口的外部变化与深链事件是否只落到最后绑定窗口应做真实验收。静态/附件请求和切库授权变化的异步交界应补充竞争时序测试；本次没有将其认定为已证实越权。浏览器直接文件模式大库扫描、图像解码峰值内存、长时间队列/监听器/Blob URL 释放也需要独立测量。

**维护建议。** 原生与浏览器有多份语义相似但不完全一致的实现，F01 是具体例子。优先建立跨后端的保存/恢复/事务行为契约与共享用例，不先做大型抽象重构。迁移验证应进入持续集成；发布结果应保留首次失败、重试次数和最终状态。历史文档的功能快照需要标日期，避免把旧版“不支持 Obsidian”等说明当成当前能力。
