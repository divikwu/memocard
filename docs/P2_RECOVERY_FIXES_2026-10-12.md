## 2. 库实例、移动和旧记录规则

实例范围由 `vaultId`、卷 UUID、目录 inode 与创建时间生成，不使用可被目录复制继承的同步文件标记。目录路径变化不改变同卷实例身份，副本和重新创建的目录则使用新的范围。本机身份映射使用相同范围，避免移动后正文笔记 ID 改变而无法关联草稿。

原路径对应的旧身份记录会复制到新范围，保留旧文件；旧挂起事务日志转移到新范围后按既有规则恢复，避免旧日志在后续打开时再次回放。没有在同步 Markdown 中写入新 ID 或重写用户内容来完成此迁移。

旧的 `<vaultId>` 草稿目录无法可靠推断属于原库还是副本，因此单独返回 `unscopedDrafts`。界面标明未绑定状态，打开笔记时不自动应用；用户选择后先创建独立恢复副本，完整提交后才按版本令牌清理被恢复的原记录。恢复失败或原记录后来变化时仍保留原版。

本机草稿范围另外记录所属库及最近目录位置。若原位置已消失，同库的旧实例草稿可作为未绑定版本被发现，用于目录身份改变后的手动恢复；原位置仍存在的其他实例草稿不会混入当前库。这不会自动认定“复制后删除原目录”就是一次搬移。兼容模式下目标笔记 ID 不同或原笔记不存在时，既有冲突保护仍生效，可使用另存副本保留内容。

自动续接依赖可读取的卷和目录身份；无法确认时拒绝绑定，避免回退到混用库 ID。实际同卷移动已通过文件系统测试；跨卷搬移的恢复分支以“复制后移除原位置、目录身份改变”模拟验证，未进行真实双卷或云提供商重新物化目录的硬件验收。

## 3. 提交点与故障处理

正文与单条属性更新在源写入前完成结果解析，并保存包含提交前/后字节及原身份映射的事务记录；随后写入源文件、身份记录，最后清理事务标记。只有这一流程成功才返回保存成功，草稿清理仍是独立的尽力操作。

身份写入失败时，现有恢复机制校验源文件仍等于日志中的提交前或提交后版本，才允许回滚。若发现外部第三种内容，返回恢复待处理状态，不强行覆盖；本机草稿仍可读写。进程中断后，尚有事务标记的操作按日志恢复；标记已经清理的操作按已提交版本读取。

响应丢失仍有明确边界：源文件可能已经提交，旧哈希再次提交会被拒绝，可以重新读取实际版本；本次没有增加网络请求的自动幂等重放。回归测试确认这种重试不会第二次改写或覆盖文件。

## 4. 回归与集成验收

新增 **10 项原生测试、4 项 UI/会话测试**。测试先复现了副本草稿串库、单条异常中断列表、身份落盘失败后源字节已经变化及旧版本重试冲突，再验证修复后的结果。

| 场景 | 断言 |
| --- | --- |
| 两种 Markdown 模式复制库、原库和副本各存草稿 | 两边记录隔离；一方提交不改变副本源文件及其草稿 |
| 同卷移动后新建 store 重开 | 原草稿、笔记 ID 保持，恢复可提交 |
| 旧格式草稿及旧身份/事务记录迁移 | 未绑定草稿不自动归属；失败保留、成功匹配清理；旧日志不重复回放 |
| 原实例消失、独立副本仍存在 | 旧实例可手动恢复；原位置仍存在时不可自动混入；非法范围拒绝且源字节不变 |
| 两份好草稿加 JSON 截断和语义非法记录 | 好记录均返回；分别报告异常路径；坏文件原字节保留，源笔记可打开 |
| 整个恢复请求失败、源笔记深链 | 正常正文仍打开，显示独立恢复异常，不误报连接断开 |
| 正文和属性的源提交后身份写入失败 | 源字节恢复为原值，正文和待保存属性保留；处理故障后原哈希可重试，重开 ID/哈希一致 |
| 新建时事务日志或身份记录不可写 | 不留下已提交的 Markdown；草稿保留；故障解除后可提交 |
| 日志准备后、源写入后、身份写入后中断 | 新 store 恢复原源字节和身份映射，草稿仍在，之后可正常提交 |
| 成功响应丢失后旧版本重试 | 拒绝旧哈希，已提交字节不变，重开读取正确版本 |

### 隔离真实浏览器

使用生产 UI、`VaultStore` 和 `LocalWebServer`，65 篇合成笔记，独立本机恢复目录。所有故障均只注入该临时服务。

1. 放入两份有效草稿和一份截断 JSON，页面显示具体坏文件路径；两个好版本可选择，源笔记深链正常打开。
2. 将身份记录路径临时替换为目录，制造源写入之后的身份落盘失败。失败后继续修改正文 A→B，并勾选属性；65 份源文件逐字节保持提交前版本，最新 B 正文和勾选意图分别保存在草稿中。
3. 解除故障后重试，磁盘正文为 B、`verified` 为 true、其他属性原值保留。离开并重新打开后，正文及勾选显示一致，当前待保存意图已清理，两份其他好草稿和坏 JSON 原文件均保留。
